---
title: Shadow mode on GitHub
description: Publish test reports from CI and run the Gate after every pull request build, without letting it merge anything.
---

Shadow mode is where every repository starts. The Gate judges each change and people keep merging. You learn how often you agree with it before it is allowed to act.

<Note>
The GitHub adapter is tested against an in-memory host that follows the same interface. It has not yet been run against live GitHub from this project's CI. Expect to report a rough edge or two. See [Status and limits](/reference/status).
</Note>

## 1. Commit a factory config

```bash
oafactory init
oafactory ready
git add .oafactory && git commit -m "Add OAFactory config"
```

Set `checks.required` to the exact names of your CI jobs. The Gate matches check names literally.

## 2. Publish a test report

`test_integrity` evidence needs a JUnit report for both the base commit and the head commit. Add an upload step to the job that runs your tests, and make sure the workflow runs on pushes to the default branch as well as on pull requests.

```yaml
name: CI
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pytest --junitxml=report/junit.xml
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: oafactory-test-report
          path: report/
```

The artifact must be named exactly `oafactory-test-report`.

| Test runner | How to produce JUnit XML |
|---|---|
| pytest | `pytest --junitxml=report/junit.xml` |
| Vitest | `vitest run --reporter=default --reporter=junit --outputFile.junit=report/junit.xml` |
| Jest | `jest --reporters=default --reporters=jest-junit` |
| Go | `go test ./... -v 2>&1 \| go-junit-report > report/junit.xml` |

Without a report, Tier 0 still works. Tier 1 changes will always escalate.

## 3. Give the Gate a place to run

The Ledger is a SQLite file that must live outside the repository and survive between runs. A GitHub-hosted runner starts empty every time, so run the Gate on a machine you control: a self-hosted runner, a small server, or your own laptop while you evaluate.

By hand, after CI finishes:

```bash
export OAFACTORY_GATE_TOKEN=...   # a token that can read checks and comment
oafactory gate 431 --repo owner/name
```

Or automatically, with a workflow on a self-hosted runner:

```yaml
name: OAFactory Gate
on:
  workflow_run:
    workflows: [CI]
    types: [completed]
jobs:
  gate:
    if: github.event.workflow_run.event == 'pull_request'
    runs-on: [self-hosted, oafactory-gate]
    steps:
      - name: Gate each pull request for this commit
        env:
          OAFACTORY_GATE_TOKEN: ${{ secrets.OAFACTORY_GATE_TOKEN }}
          OAFACTORY_LEDGER: /var/lib/oafactory/ledger.db
          PRS: ${{ toJson(github.event.workflow_run.pull_requests.*.number) }}
        run: |
          for n in $(echo "$PRS" | tr -d '[],'); do
            oafactory gate "$n" --repo "$GITHUB_REPOSITORY"
          done
```

`workflow_run` always uses the copy of the workflow on the default branch, so a pull request cannot change what the Gate runs. Keep `.github/` in `protected` regardless.

## 4. Record outcomes

Run the Watcher on a schedule. In shadow mode it does not revert anything; it records whether each would-merge change was merged unchanged, closed, or reverted.

```bash
oafactory watch --repo owner/name --every 60
```

## 5. Read the results

```bash
oafactory standing --repo owner/name
oafactory scoreboard
```

When a tier shows as eligible and you trust what you have seen, move on to [earned mode](/guides/earned-mode).

## Keep branch protection on

Branch protection and code-owner rules on protected paths must stay enabled. The Git host is the last line of defence against a defect in the factory itself.
